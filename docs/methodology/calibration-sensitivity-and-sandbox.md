# 标定敏感度与沙盘作业法 (Calibration Sensitivity & Sandbox)

## 1. 概述与适用范围

本文回答一个问题：**改动 `RatingOptions` 的任一标定常数，段位阶梯会怎么动？**

需要这个答案的场合有三个：

- 想调整难度标尺（整体平移、改曲率、改聚合成型）；
- 验收线要重新基线化时，判断新点位是否仍落在闸门内；
- 有人报告某个常数"看起来不对"，需要先知道动它的代价再决定要不要动。

本文的结论**全部是在 120 首冻结标杆语料上实测的**，不是推导。方法与工具见第 2 节，可复现；结论见第 4–7 节；过程中踩过的三个坑见第 9 节——**第 9 节比结论更重要**，因为结论会随标定变化，坑不会。

---

## 2. 沙盘作业法

### 2.1 为什么能快

星级由两段组成，两段对常数的依赖完全不同：

| 段 | 内容 | 是否读标定常数 |
| :--- | :--- | :--- |
| 上游 | 特征张量、双手应变时序、8 维原始驱动 | **否** |
| 下游 | 锚定律、回压指数、p-Norm 聚合、tanh 软压缩 | **是** |

因此上游对 120 首谱面**只需算一次并冻结**，之后每个标定点的重算只剩纯算术。全套九常数扫描几秒跑完，而不是几十分钟。

这是沙盘的全部原理。它不近似、不简化模型——冻结的是真实的特征与真实的驱动，下游调用的也是真实的 `rating.synthesize_star_rating`。

### 2.2 唯一的硬性前提：自校验

**冻结核心必须能逐位复现 `evaluate_intrinsic_difficulty`，否则不许给结论。**

工具在每次运行开始断言这一点，偏差超过 `1e-9` 星直接拒绝运行。这不是形式主义：本次作业中我自己的阶梯度量实现错过一次（见 9.1），若没有这道断言，整轮扫描的 PASS/FAIL 都会建立在一个与真实引擎不同的度量上。

### 2.3 工具

```bash
# 基线：当前标定的阶梯事实与四条锚点带的余量
PYTHONPATH=src python3 tools/calibration_sandbox.py

# 单点评估：给一组常数，看它是否过闸门、阶梯怎么动
PYTHONPATH=src python3 tools/calibration_sandbox.py --set strain_a=0.242 --set soft_cap_scale=2.0

# 全量单因子扫描
PYTHONPATH=src python3 tools/calibration_sandbox.py --sweep

# 机器可读
PYTHONPATH=src python3 tools/calibration_sandbox.py --set strain_exp=0.6175 --json
```

冻结核心缓存在 `.cache/proj7k-sandbox/`，**以引擎源码摘要为失效键**，而不是以方法学指纹——因为扫描的对象恰恰是会被指纹记录的那些常数，但上游的改动（见第 8 节）指纹记录不到。摘要法对两者都成立。

闸门阈值直接读 `guard.CALIBRATED_METRIC_GATES`，锚点带直接读 `dan.CANONICAL_DAN_SR_BANDS`，不在沙盘里重打一份——**阈值重新标定时两者一起动**。

## 3. 当前标定的基线事实

> 实测于 `main`（`c32a2ad`），`current_engine_version() = v341f77d8`。常数变更后本节全部数字需重测——**包括这个版本号本身**：任何一个标定常数的改动都会移它，而本节下面的阶梯统计不会动。版本号是快照，不是稳定标识。
>
> 版本号在 #48 之后由 `v2c6bbe75` 变为本值——因为指纹的**取数范围**变了（雷达/特征的字面量已并入），而非因为任何星级的数值变了。本节以下的全部数字（阶梯统计、锚点中位数、星级指纹）**与 #48 之前逐位相同**，这正是本票「纯重构」的验收条件。


## 4. 结论一：真正的闸门是锚点带，不是秩相关

扫描中几乎所有点位的 `τ`、`ρ`、倒挂数**纹丝不动**（τmin 稳在 0.905，ρmin 稳在 0.964）。

原因很直白：最终星级是应变 P90 的单调函数，而 P90 随段位单调，所以阶梯形状天然抗扰动。**PASS/FAIL 几乎完全由四个锚点中位数是否落在带内决定。**

> **实践含义**：想让闸门拦住某类改动时，别指望单调性检查。`--guard-metric` 加原始密度特征、或缩小锚点带，才是提高分辨率的杠杆。

---

## 5. 结论二：安全窗是 −10% … +6%

三档的上行余量一致压在 **6% 左右**（见第 3 节表）。

这意味着，**任何把星级标尺整体抬高超 ~6% 的改动，必定在 0th / 5th / 10th 上撞带挂 CI**——跟你改得对不对无关。下行宽松得多（约 10%–20%），因为基线中位数在各自带内偏下。

这不是"预期"或"经验法则"，是四条带在当前基线位置上的直接算术后果。改动标尺前先用沙盘看一眼新点位，比事后调带便宜得多。

---

## 6. 结论三：旋钮分级

单因子扫描结果（其余常数保持默认）：

| 常数 | 默认 | 测试范围 | 结果 |
| :--- | ---: | :--- | :--- |
| `strain_exp` | 0.65 | ×0.85 ~ ×1.15 | **全部 FAIL** — 最敏感，±5% 即破 10th |
| `strain_a` | 0.268980 | ×0.75 ~ ×1.25 | ×0.9 过；×1.1 挂 |
| `strain_b` | 0.129915 | ×0 ~ ×4 | ×0 ~ ×2 过；×4 挂（纯加性偏移，宽容） |
| `p_norm` / `damping_coeff` / `driver_backpressure_exp` | — | — | **已删除**（#50：合成改 max、分值改绝对标定，见 `docs/adr/0016`）|
| `technique_anchors`（8×a/exp） | 见 `calibration.py` | — | 不是一维扫描对象：逐轴拟合用 `tools/technique_star_fit.py` |
| `soft_cap_threshold` | 9.5 | ×0.9 ~ ×1.1 | 全 PASS |
| `soft_cap_scale` | 3.0 | ×0.5 ~ ×2.5 | 全 PASS |
| ~~`max_star_rating`~~ | — | — | 字段已随 #48 删除 |
两条值得单独拎出来：

**`max_star_rating` 曾是死常数**（已随 #48 删除）。它不参与任何钳制，120 张谱星级一张不动；真正的天花板来自 `soft_cap_threshold + soft_cap_scale = 12.5`。改它到 8.0 或 20.0，**只有方法学指纹会变**——得到一个改了版本号、作废了缓存、却没改任何数值的结果。删除而非接线，是因为 tanh 软上限的渐近线本就是一个取不到的封顶：任何 ≥12.5 的硬钳制永不可达，<12.5 的则给一条为光滑而存在的曲线加上硬拐点。

**压缩算子几乎不受约束。** `soft_cap_*` 随便动都过闸门，因为全语料只有 16~24 张谱超过 9.5★，且它们全落在 Stellium 档——那一档的带 [10.0, 12.5] 宽达 2.5★。**真想约束压缩行为，现有四条带是约束不住的。**

**方向性**：几乎所有"抬高难度"的扰动都挂（`strain_a` 上行、`strain_b` 上行、`strain_exp` 上行），"降低难度"的扰动才有空间。响应是不对称的。**本节的下表与"上行余量"是 `c32a2ad` 时的快照（见 #51 交接 §4.10），#50 之后应变侧常数只影响 fallback 与 `raw_strain_rating`，扫描已基本饱和**——方法仍有效，数字不再代表当前标定。

## 7. 结论四：不要拿 τ 的 0.019 当改善依据

扫描中有三个点同时满足"过闸门"与"τmin/ρmin 更高"：

```
```

拆开看，所谓的改善是：

```
基线            LN Inverse  τ 0.9048  =  5 个倒挂对 / 105
driver_bpe 0.975 LN Inverse  τ 0.9238  =  4 个倒挂对 / 105   ← 少了一个对
```

15 级阶梯的 Kendall τ 分辨率是 `2/105 ≈ 0.019`，所以 0.905 → 0.924 是**一个倒挂对翻了过来**，一次离散跳变，不是稳健改善。三者都停在同一个数值上正是这个原因——它们各自把最差维度推过了同一个台阶。

> **实践含义**：任何"改常数让秩相关变好"的入选理由，先换算成倒挂对数再判断。少于 2 个对的差异不要当成依据。

## 8. 指纹覆盖范围：曾经的缺口，以及它是怎么堵上的

本节曾记录一个**已修复**的缺口。留档在此，因为它的形状比结论更有复用价值。

### 8.1 曾经的缺口（#48 之前）

`difficulty.DifficultyOptions.engine_fingerprint` 的文档声称覆盖"every constant that can move a star rating"，而实测不成立：`radar.py` / `features.py` 的函数体内散着约 40 个能移动星级的字面量，全部在指纹之外。实证（不修改仓库，把 `radar.py` 源码替换一个字面量后在临时命名空间重新 exec，用真实算子重算）：

```
radar.py:328   supp = max(0.05, 1.0 - 3.6 * max(0.0, jack_ratio - 0.11))
                                3.6 → 5.0

engine version BEFORE: v2c6bbe75
engine version AFTER : v2c6bbe75     ← 完全不变
星级变化: 10/120 张，最大 0.0565★
```

**后果**：本仓库的 CI 会被星级指纹测试拦住，但 ADR-0014 的机制——把已注入 osu!lazer 的谱标记为陈旧并重评——**不会触发**，旧注入会静默保留旧星级与段位标签。这正是 ADR-0014 要防的那个失效模式。

反面同时存在：`max_star_rating` 进了指纹，却没有任何代码读它（见第 6 节）。指纹既漏又溢。

### 8.2 现在（#48 之后）

同一个 `3.6 → 5.0` 的改动，现在落在 `RadarOptions.stream_jack_supp_gain` 上，实测量级完全不变：

```
engine version BEFORE: v341f77d8
engine version AFTER : v5a6e117c     ← 必变
星级变化: 10/120 张，最大 0.0565★   ← 与 8.1 逐位相同，说明这是纯重构
```

堵住缺口的是**四道互补的机制**，缺一道都不成立：

| 机制 | 位置 | 拦住什么 |
| :--- | :--- | :--- |
| 选项对象整体入指纹（`asdict`） | `difficulty.py` | 新增一个标定字段而忘了进指纹 |
| 参数化覆盖测试 | `tests/test_calibration.py` | 逐字段断言：任一字段改动必移 `current_engine_version()` |
| 字面量登记守卫 | `tests/test_engine_literal_registry.py` | 函数体内出现未登记的数值字面量 |
| 模块常量申报 + 字段读取断言 | 同上 | 同一个常数换门而入 |

前两道只能保证「已登记的常数都进了指纹」，管不住「还有常数没登记」。后两道把这条变成可执行的，且各自守着一扇门：

- **函数体内的字面量**：AST 读出星级路径各模块函数体内的全部数值字面量，要求与登记表**逐值逐次**精确吻合，多一个、少一个、改一个都失败。留在函数体里的只剩非标定字面量（代数恒等、下标与计数、单位换算、哨兵、epsilon），每一条都在登记表里写明理由。
- **模块级常量**：把一个标定字面量从函数体搬到模块级，就同时躲开了上面那道扫描——除非该模块在 `CALIBRATION_CONSTANTS` 里申报它，否则指纹也看不见它。守卫因此同时要求：扫描到的每个模块级数值常量，都必须在它所属常数块的申报清单里。
- **「进了指纹」不等于「被用过」**：`max_star_rating` 当年正是被枚举进指纹、却没有任何算子读它。守卫断言四个选项对象的**每一个字段**都在 `*_fingerprint` 之外的某处被当作属性读取过——只出现在指纹枚举里的字段，就是空旋钮。

标定常数因此只有两条出路，都必须显式：**给出一个家**（`RatingOptions` / `RadarOptions` / `FeatureOptions` / `StrainOptions` 的字段，或 `physics` / `scaling` / `strain` 的具名常数块），**或在此写明它为什么不需要家**。前者自动进指纹，后者进登记表。

顺带一提，这个「守卫的守卫」不是多余的：本票实现过程中，`StrainOptions.tau_half_life_s`（第三个空旋钮）与 `strain.CENTER_SHARED_LANE`（声明了却无人读取的共享中键）都是靠它才被发现的。


### 8.3 顺带发现的重复

同一批字面量里藏着几处**同一常数两份拷贝**，本票一并收敛（值不变，行为逐位一致）：

- `strain.compute_high_speed_scaling_factor` 硬编码的 `145.0 / 180.0`，与 `scaling.py` 的同名 BPM 阈值是同一个数——现在读同一份定义。
- 判定窗 `38.0` 曾有三份（`StrainOptions.w_judg_ms`、`RadarOptions.w_judg_ms`、`compute_judgment_overlap_buffer` 的默认值）——现由 `physics.JUDGEMENT_WINDOW_MS` 单点定义；顺带发现 `RadarOptions.w_judg_ms` 与 `max_star_rating` 一样无人读取，已删除。
- 微爆发律的 `5.0 / 50.0 / 1.35` 在应变侧与雷达侧各写一遍——现由 `physics.SPEED_BURST_*` 单点定义。
- `radar.compute_tech_4d_components` 把三处 4D 权重重打了一遍——现读 `RadarOptions` 的同名字段。

**一处已知未收敛**：`strain.compute_8d_strain_timeseries`（降阶器侧）仍自行重写了叠键饱和律与微爆发律。它消费雷达、产出练习谱的目标应变曲线，在星级评级的**下游**，动不了任何星级，因此在登记表里作**显式豁免**并写明了理由——守卫的作用是让它可见，不是假装它不存在。

## 9. 三个已经踩过的坑

### 9.1 偶数样本的中位数

每个段位只有 **8 张谱**（8 技法 × 1），是偶数样本。`statistics.median` 取中间两者均值，我起初取了中间偏上的那个，于是 0th 报成 3.97 而非 3.763——四个中位数全偏，整套 PASS/FAIL 判定随之偏移。

**教训**：自建的阶梯度量在用于判断之前，必须先与仓库既有产物对齐到小数点后三位（护栏的锚点摘要、`tests/conftest.py` 的夹具、或星级指纹）。对不齐时不要解释，先修自己的实现。

### 9.2 护栏的 `max_violations` 是每技法上限

`MonotonicityGuardConfig.max_violations = 4` 作用于**单个技法的阶梯**，不是八技法的倒挂总和。我按总和算，基线直接报 FAIL（16 > 4）。

**教训**：`guard.py` 里每条阈值的**作用域**（每技法 / 全阶梯 / 每谱）必须读源码确认，不能从名字推断。

### 9.3 基线对不上时，先怀疑自己的度量

本次出现基线数值对不上时，我先假设了两个外部原因，**均验证为否**：

- *陈旧 Layer-2 缓存*（真实旧疾，本仓自己复述它的两处：`tools/calibration_sandbox.py:77` 的 `_source_digest` docstring、物证 `src/proj7k/cache.py:13` 的 `ALGORITHM_VERSION`）：开缓存与完全禁用缓存跑出的星级指纹与四个中位数**完全一致**，当前没有发作。
- *BPM 双源*：manifest BPM 与谱面自身支配 BPM 只有 1 张不同（LN Inverse 6th，78.96 vs 78.85），且 0 张谱星级受影响。

真因是自己的中位数实现（9.1）。

**教训**：这两个假定都有真实历史依据，所以更有迷惑性。基线偏差的排查顺序应当是——自己的度量 → 自己冻结的核心 → 引擎路径 → 外部依赖。

## 10. 复现

```bash
# 1. 沙盘自校验 + 基线（首次运行会重建冻结核心，约 30 秒）
PYTHONPATH=src python3 tools/calibration_sandbox.py

# 2. 本文第 6 节的旋钮分级表
PYTHONPATH=src python3 tools/calibration_sandbox.py --sweep

# 3. 本文第 8 节的指纹覆盖：两道可执行的守卫
PYTHONPATH=src python3 -m pytest -q tests/test_calibration.py tests/test_engine_literal_registry.py
```

第 8.1 节的缺口实证（#48 之前）是一次性脚本，从未进仓库：读取 `src/proj7k/radar.py` 源码文本，替换目标字面量后 `exec` 进一个临时 `types.ModuleType`，调用其 `compute_raw_technique_drivers` 得到新驱动，再经第 2.1 节的下游算术算出星级，与基线逐谱比对；同时打印 `current_engine_version()` 前后值。全程不写仓库。

第 8.2 节的复现不需要这种手法——那里改的是一个真正的选项字段，直接构造即可：

```python
moved = DifficultyOptions(radar_options=RadarOptions(stream_jack_supp_gain=5.0))
evaluate_intrinsic_difficulty(content, options=moved)   # 星级会动
current_engine_version() != before                      # 版本也会动
```
